# Dogfight - Лабораторна робота №1: The Event Loop Is the Game Loop

Перший етап гри Dogfight: кероване судно на Canvas 2D з ігровим циклом на фіксованому кроці
симуляції (fixed timestep + accumulator), інтерполяцією відмальовування та переносом через краї
арени.

## Можливості

- Поворот: `←` `→` або `A` `D`. Тяга: `↑` або `W`.
- Інерція, лінійний опір, стеля швидкості.
- Безшовний перенос через краї екрана (судно малюється з обох боків межі).
- Фіксований крок симуляції 1/60 с незалежно від частоти екрана (60/120/144 Гц).
- Інтерполяція позиції та кута між кроками (кут - за найкоротшою дугою).
- Зоряне небо та сітка, полум'я двигуна під час тяги.
- HUD: `Steps/s` (~60), `FPS` (частота екрана), `Frame time` (мс CPU на simulate + render).
- Canvas враховує `devicePixelRatio` і перебудовується під час зміни розміру вікна.

### Запуск подвійним кліком (без сервера)

`dist/index.html` відкривається прямо з файлової системи (`file://`). Chrome і Edge блокують
`<script type="module">` та ресурси з `crossorigin` на `file://` (origin `null`), тому
`vite.config.js` робить два кроки під час збірки:

1. випускає бандл одним класичним IIFE-скриптом (`build.rollupOptions.output.format = 'iife'`);
2. плагін `file-protocol-compat` замінює в `index.html` `<script type="module" crossorigin ...>` на
   `<script defer src="./assets/...">`.

Усі шляхи відносні (`base: './'`). Імена файлів збірки - лише в нижньому регістрі (hex-хеш), тому
вони однаково працюють на macOS, Windows і Linux. Режим `npm run dev` досі використовує нативні
ES-модулі.

## Архітектура

```
requestAnimationFrame ──> frame(time)
                            │ dt = min(Δt, 0.25)
                            │ accumulator += dt
                            │ while accumulator >= 1/60:
                            │     simulate(1/60)   // введення -> integrate -> wrapShip -> endStep
                            │ render(alpha = accumulator / (1/60))
```

- **Фіксований крок.** Стан змінюється лише кроками по 1/60 с. Результат симуляції не залежить
  від частоти кадрів і навантаження машини.
- **Кламп дельти** `Math.min(dt, 0.25)` обмежує роботу за кадр 15 кроками. Після паузи (прихована
  вкладка, відлагоджувач) цикл не намагається «наздогнати» хвилини реального часу - «спіраль
  смерті» виключена.
- **Метрики** рахуються у вікні 500 мс: `stepsPerSec` (кроків симуляції за секунду), `fps` (кадрів
  rAF за секунду), `frameTimeMs` (CPU-час simulate + render останнього кадру).
- **Інтерполяція.** Перед кожним кроком `integrate` копіює `x, y, angle` у `prevX, prevY,
prevAngle`. `render` малює стан у точці `lerp(prev, current, alpha)`, тому рух плавний на
  екранах 120/144 Гц, де кадрів більше, ніж кроків. Кут інтерполюється за найкоротшою дугою
  (`lerpAngle`): під час переходу через ±π судно не робить оберт на 360° за один кадр.
- **Перенос через край.** `wrapShip` віднімає від `x, y` кратне розміру арени і **зсуває на ту саму
  величину** `prevX, prevY`. Відрізок `prev -> current` лишається коротким, і інтерполяція не
  протягує судно через увесь екран. Просте присвоєння `prev = current` дало б стрибок позиції на
  один кадр. Біля краю судно додатково малюється з протилежного боку.
- **Введення.** `createInput` зберігає два приватні `Set` у замиканні. `justPressed` скидається
  `endStep()` після кожного кроку. У `main.js` клавіша активна, якщо її утримують _або_ натиснули
  від минулого кроку: тап, коротший за крок симуляції, не губиться. Використовуються
  `KeyboardEvent.code` (фізичні клавіші), тому керування не залежить від розкладки. Після втрати
  фокуса вікна введення скидається.

## Фізика судна

Одиниці: пікселі, секунди, радіани. Інтегратор - напівнеявний Ейлер (спочатку швидкість, потім
позиція).

| Параметр      | Значення   | Обґрунтування                                                          |
| ------------- | ---------- | ---------------------------------------------------------------------- |
| `turnRate`    | 3.4 рад/с  | Оберт за 1.85 с, поворот на 90° за 0.46 с: чуйно, але точно            |
| `thrustAccel` | 420 пкс/с² | Помітний розгін: 240 пкс/с за ~0.75 с                                  |
| `drag`        | 0.75 1/с   | Швидкість спадає вдвічі за ln2/0.75 ≈ 0.92 с: судно ковзає             |
| `maxSpeed`    | 480 пкс/с  | Екран 1000 пкс перетинається за ~2 с; нижче за межу `thrustAccel/drag` |

- Опір застосовується як `v *= e^(-drag·dt)`. Це точний розв'язок рівняння `v' = -drag·v` для
  кроку `dt`, він не залежить від розміру кроку (на відміну від `v *= 1 - drag·dt`).
- Без стелі швидкість прямувала б до `thrustAccel / drag = 560 пкс/с`. Стеля 480 пкс/с
  спрацьовує приблизно через 2.6 с безперервної тяги й не дає судну стати некерованим.
- Судно зберігає інерцію: після відпускання тяги воно летить далі, а поворот змінює лише
  напрямок прискорення, а не вектор швидкості - це й дає відчуття «космічного» керування.
- `integrate` - чиста функція: вона не звертається до DOM і Canvas та працює в Node (на цьому
  побудовано експеримент у розділі 3).

### 1. Чому блокування на 100 мс у `render` заморожує вкладку

JavaScript виконується в одному потоці за моделлю run-to-completion: доки функція не повернула
керування, Event Loop не може взяти наступне завдання. Колбек `requestAnimationFrame`, введення
(`keydown`), таймери та саме відмальовування сторінки стоять у чергах головного потоку. Браузер не
може витіснити синхронний код, тому цикл `while (performance.now() < end);` на 100 мс утримує
потік 100 мс поспіль, і ніщо на цьому потоці не обходить цю чергу: ні `setTimeout(0)`, ні
`Promise` (мікрозавдання виконуються після поточного коду, а не замість нього).

В експерименті це видно в цифрах: за блокування 100 мс `Frame time` дорівнює 100.1 мс, FPS падає з
60 до 10, кадр віддає весь доступний час головного потоку (інтерфейс вкладки не отримує вільних
проміжків), а реакція на клавішу відкладається до 100 мс. Акумулятор при цьому зберігає швидкість
гри: кожен кадр виконує по 6 кроків, `Steps/s` лишається 60. За блокування 300 мс дельта
клампиться до 0.25 с, за кадр виконується не більше 15 кроків, `Steps/s` падає до 50: гра навмисно
йде в уповільненому часі, а не намагається наздогнати реальний. Обійти блокування можна лише
виходом за межі однопотокової моделі: важку роботу переносять у Web Worker (окремий потік і свій
Event Loop) або розбивають на шматки між кадрами.

### 2. `requestAnimationFrame` проти `setInterval(frame, 16)`

Виміряно за 3 секунди за вільного головного потоку (інтервали між викликами, мс):

| Джерело                 | Викликів | Середнє | σ    | Максимум |
| ----------------------- | -------- | ------- | ---- | -------- |
| `requestAnimationFrame` | 180      | 16.67   | 0.06 | 16.8     |
| `setInterval(…, 16)`    | 187      | 15.99   | 0.67 | 17.5     |

- `rAF` викликається браузером перед відмальовуванням, прив'язаний до частоти дисплея (v-sync) і
  підлаштовується під 120/144 Гц. Його інтервал майже не тремтить (σ = 0.06 мс).
- `setInterval(…, 16)` живе на власному годиннику й не знає про дисплей. Період 16 мс не дорівнює
  16.67 мс, тому за 3 с набігло 187 викликів на 180 кадрів: приблизно кожен 25-й кадр отримує два
  оновлення, а фаза відносно v-sync безперервно пливе - виникає періодичне смикання. Тремтіння
  вище в 10 разів (σ = 0.67 мс), а під навантаженням таймер ще й зсувається чергою завдань. До
  того ж колбек таймера не гарантує, що після нього буде кадр відмальовування.
- Фонова вкладка (поведінка браузерів за документацією, тут не вимірювалась): `rAF` повністю
  призупиняється, гра не витрачає CPU; таймери сповільнюються до одного виклику за секунду (у
  Chrome після 5 хвилин у фоні - до одного за хвилину). Цикл на `setInterval` або перетворить гру
  на 1 крок за секунду, або, рахуючи дельту за годинником, отримає гігантський `dt`, який без
  клампінгу призведе до «спіралі смерті».

### 3. Чому змінний крок (без акумулятора) ламає детермінізм

Експеримент у Node: один і той самий сценарій введення (тяга 0-3 с, праворуч 0.5-1.2 с, ліворуч
2.0-2.4 с) прогнано в `integrate()` на 5 секунд симуляції за різних послідовностей тривалості
кадрів. Еталон - фіксований крок 1/60 за 60 Гц. Розбіжність - відстань до еталонної позиції:

| Частота кадрів               | Фіксований крок | Змінний крок (`dt` = час кадру) |
| ---------------------------- | --------------- | ------------------------------- |
| 144 Гц                       | 0.00 пкс        | 34.91 пкс                       |
| 60 Гц                        | 0.00 пкс        | 0.00 пкс (кадр збігся з кроком) |
| 10 FPS (аналог тротлінгу ×6) | 0.00 пкс        | 70.51 пкс                       |
| тремтіння 4-104 мс           | 0.00 пкс        | 159.79 пкс                      |

Причини розбіжності за змінного кроку:

1. **Похибка дискретизації залежить від `dt`.** Напівнеявний Ейлер має похибку порядку `dt`:
   інший набір кроків дає іншу траєкторію навіть із тим самим введенням.
2. **Нелінійність** (стеля швидкості) застосовується на кожному кроці й не комутує з розбиттям
   часу.
3. **Квантування введення.** Натиснута клавіша діє на весь кадр цілком: за 100 мс на кадр поворот
   у 0.7 с перетворюється на 7 дискретних поштовхів, а за 7 мс - на 100.

Траєкторія стає функцією продуктивності машини, а не гри: не можна зробити повтор (replay),
синхронізувати мережу за входами (lockstep) чи написати відтворюваний тест. Фіксований крок з
акумулятором виконує рівно ту саму послідовність викликів `simulate(1/60)`, а частота кадрів
впливає лише на інтерполяцію в `render`.

Чесне застереження: за реального тротлінгу ×6 ця легка сцена й надалі трималась на 60 кроках/с і
60 FPS (робота кадру 0.1-0.8 мс вкладається в бюджет 16.7 мс із запасом), тому рядки «10 FPS» і
«тремтіння» в таблиці вище - модель такого навантаження, а не її запис із браузера. Реальний цикл
у такій ситуації показано в рядках із блокуванням 100/300 мс із таблиці вимірювань.

## Prove It To Yourself — Результати експериментів

_Усі заміри виконано в Node.js `v26.13.1` на цільовій машині._

### 1. Порядок виконання в Event Loop

Запуск одноразового скрипта із синхронним кодом, `Promise.resolve().then(...)`, `queueMicrotask(...)` та `setTimeout(..., 0)` дав такий фактичний порядок:

```text
1:sync-start -> 1b:sync-end -> 3:Promise.then -> 2:queueMicrotask -> 4:setTimeout(0)
```

**Висновок:** спершу повністю виконується поточний call stack (`sync-start` → `sync-end`), далі очищується вся черга мікрозадач (у порядку додавання: `Promise.then`, `queueMicrotask`), і лише на наступній фазі циклу подій запускається макрозадача `setTimeout(..., 0)`.

### 2. Джитер `setInterval(..., 16)` проти Fixed Timestep (`dt = 1/60`)

На 100 ітераціях `setInterval(..., 16)` у Windows-таймері (крок системного переривання ~15.6 мс) зафіксовано:

| Метрика                                  | Фактичне значення |
| ---------------------------------------- | ----------------: |
| Ітерацій `setInterval(..., 16)`          |               100 |
| `min dt`                                 |     **15.583 ms** |
| `avg dt`                                 |     **28.889 ms** |
| `max dt`                                 |     **31.511 ms** |
| Кроків fixed timestep (`dt = 16.667 ms`) |           **173** |

**Висновок:** реальний інтервал таймера ОС нестабільний (`15.58`–`31.51 ms`), тому пряме `pos += vel * rawDt` призводить до «плаваючої» фізики. Акумулятор fixed timestep (`while (acc >= FIXED_DT)`) завжди інтегрує фізику строго кроками по `16.667 ms`, а обмеження `dt = Math.min(rawDt, MAX_DT)` (`clamp dt`) захищає від «телепортації» корабля й прольоту крізь астероїди після повернення зі згорнутої вкладки.
