# Dogfight - Лабораторна робота №2: Objects, Prototypes, and this: The Entity Model

Другий етап гри Dogfight: повноцінна модель сутностей (судно, кулі, астероїди, бонуси, вибухи),
стрільба, зіткнення, шкода, респаун і композиція поведінок (самонаведення, бонуси). Основа -
ігровий цикл із фіксованим кроком з Лаби №1 (її знімок і докладний розбір - у `Lab_1/`).

## Можливості

- **Судно** (`Ship extends Entity`): здоров'я `#hp`, стрільба кулями, ракети з самонаведенням,
  невразливість після влучання та респауну, бонусні ефекти.
- **Кулі** (`Bullet`): час життя, швидкість, шкода; власні кулі судно не зачіпають.
- **Астероїди** (`Asteroid`): дрейф, обертання, перенос через краї, запас міцності, очки за
  знищення. Великі й середні розпадаються на два менших. Приблизно 30% астероїдів - «мисливці»
  (червоні): до них приєднано компонент самонаведення, і вони повільно повертають до судна.
- **Бонуси** (`pickup`): аптечка `+` (+35 HP) і скорострільність `»` (rapid fire, 8 с).
- **Вибухи** (`Explosion`): короткоживучі частинки при знищенні судна й астероїдів.
- **Респаун**: через 2 с після загибелі судно відроджується в найбезпечнішій точці арени з 2 с
  невразливості.
- **HUD** (ліворуч угорі): Steps/s, FPS, Frame time, HP (число й смуга), Score, активні бонуси.
- Фіксований крок 1/60 с, інтерполяція позиції й кута (`alpha`), перенос через краї без швів,
  підтримка `devicePixelRatio` - усе з Лаби №1.

## Модель сутностей

### Entity і однорівневе успадкування

`Entity` - єдиний базовий клас. Поля: `pos`, `prevPos` (для інтерполяції), `vel`, `angle`,
`prevAngle`, `radius`, `alive = true`, `kind`, метод `update(dt)`. Унікальний номер зберігається в
приватному полі `#id = Entity.#nextId++` зі статичним приватним лічильником і віддається через
геттер `get id()`: ззовні його не можна ні прочитати в обхід геттера, ні змінити.

`Ship`, `Bullet`, `Asteroid`, `Explosion` успадковуються безпосередньо від `Entity`: ланцюжок
прототипів завжди `X.prototype -> Entity.prototype -> Object.prototype`. Глибших ієрархій немає.
Усе, що «додається» до сутності (самонаведення, підбір, час життя), підключається композицією - див.
розділ нижче.

### Vector2

Методи `add`, `sub`, `scale`, `normalize`, `rotate` повертають **новий** вектор і не чіпають
`this`; `length` і `dot` повертають число; `Vector2.fromAngle(angle)` - статична фабрика. Для гарячих
шляхів (`update` кожної сутності 60 разів на секунду) є мутуючі `addInPlace`, `addScaledInPlace`,
`scaleInPlace`, `set`, `copyFrom` - вони не створюють об'єктів, тож не навантажують збирач сміття.

### World

Сховище - приватна `Map<id, Entity>` (`#entities`):

- `spawn(entity)` додає сутність і виставляє `entity.world`;
- `despawn(id)` - **відкладене** видалення: лише `alive = false`. Фізично мертві сутності
  прибираються наприкінці `step()` (`#sweep`), тому `despawn` безпечно викликати під час обходу
  світу. Ключі для видалення збираються окремим масивом - `Map` не змінюється під час ітерації;
- `get(id)` повертає лише живу сутність;
- `*[Symbol.iterator]()` віддає всі сутності, `*ofKind(kind)` - сутності вказаного виду;
- `step(dt, input)`: поведінки (`runBehaviors`) -> `update` усіх сутностей і перенос через краї ->
  зіткнення -> правила (поява астероїдів і бонусів, респаун) -> очищення мертвих.

Світ детермінований: замість `Math.random` використовується `createRng(seed)`. Два світи з
однаковим seed і однаковим введенням дають однаковий стан.

### Зіткнення

`sim/collision.js` - окрема система: `findCollisions(world)` повертає масив пар `[a, b]` кіл, що
перетинаються (з урахуванням «склеєних» країв арени), і **нічого не змінює**. Зараз це перебір
O(n²); контракт «світ -> пари» дозволяє замінити реалізацію на просторовий хеш, не чіпаючи `World`.
Наслідки зіткнень вирішує `World`:

| Пара                | Результат                                                            |
| ------------------- | -------------------------------------------------------------------- |
| куля - астероїд     | куля зникає, астероїд отримує шкоду; знищений - очки, вибух, уламки  |
| судно - астероїд    | пружне відбиття; судно втрачає `10 × розмір` HP (якщо не невразливе) |
| судно - бонус       | застосовується ефект, бонус зникає                                   |
| астероїд - астероїд | пружне відбиття                                                      |

Інші параметри: куля - 10 шкоди, ракета - 25, судно має 100 HP й 0.6 с невразливості після влучання;
астероїди розмірів 3/2/1 мають радіус 38/24/13, міцність 30/20/10 і дають 50/30/20 очок. Після
загибелі судна світ запускає вибух і таймер респауну; точка відродження - найвіддаленіша від
перешкод серед 32 випадкових кандидатів.

## Баг втрати контексту `this` на прикладі `ship.fire`

### Чому він виникає: 4 правила визначення `this`

Значення `this` у звичайній функції задається **місцем і способом виклику**, а не місцем оголошення.
У порядку пріоритету:

1. **`new`-прив'язка**: `new F()` - `this` це щойно створений об'єкт.
2. **Явна прив'язка**: `f.call(obj)`, `f.apply(obj)`, `f.bind(obj)` - `this === obj`.
3. **Неявна прив'язка**: `obj.method()` - `this === obj`, тобто об'єкт ліворуч від крапки в момент
   виклику.
4. **Типова (default) прив'язка**: просте `f()` - `this === undefined` у strict mode (модулі й тіла
   класів завжди strict) або `globalThis` у нестрогому коді.

Стрілкові функції не входять до цих правил: вони не мають власного `this` і беруть його лексично з
оточення.

`ship.fire` - це просто посилання на функцію. Щойно його **відокремлюють** від `ship` і передають
як колбек, правило 3 перестає працювати, і `this` визначає той, хто викликає.

### Три відтворення (перевірено запуском у Node на методі з прототипу, без `bind`)

```js
const fire = Ship.prototype.fire; // те саме, що `const fire = ship.fire` без прив'язки

fire();
// TypeError: Cannot read properties of undefined (reading 'alive')   <- правило 4, strict mode

fire.call(domLikeTarget);
// null - тихо нічого не сталося: this - сторонній об'єкт без поля alive
// (DOM викликає обробник з this === currentTarget, наприклад window)

const binding = { codes: ['Space'], run: fire };
binding.run();
// null - тихо нічого не сталося: правило 3, this === binding, а не судно
```

Третій випадок - це реальний шлях у `main.js`: клавіші зіставлені з діями в таблиці `bindings`, і
дія викликається як `binding.run()`. Найнебезпечніші варіанти 2 і 3: помилки немає, постріл просто
мовчки не відбувається, бо захисна перевірка `if (!this.alive ...)` бачить чужий `this`.

### Яке виправлення обрано

У конструкторі `Ship`:

```js
this.fire = this.fire.bind(this);
this.fireMissile = this.fireMissile.bind(this);
```

Після цього `ship.fire` - власна властивість екземпляра з жорстко прив'язаним `this` (правило 2), і її
можна безпечно передавати будь-куди: в `addEventListener`, у таблицю прив'язок, у `setTimeout`.
Оригінальний метод при цьому лишається на `Ship.prototype`. Перевірка: відокремлений виклик
`const f = ship.fire; f()` створює кулю, а не падає.

### Альтернативи

| Спосіб                                        | Плюси                                                                                                    | Мінуси                                                                                                                 |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `bind` у конструкторі (**обрано**)            | безпечно в будь-якому місці виклику; метод лишається на прототипі; перевіряється й підміняється в тестах | по копії на екземпляр; про кожен метод-колбек треба пам'ятати                                                          |
| Стрілкове поле класу `fire = () => { ... }`   | коротко; лексичний `this` без `bind`                                                                     | метод не на прототипі: недоступний `super.fire()`, не підміняється через прототип; копія на екземпляр                  |
| Обгортка на місці виклику `() => ship.fire()` | клас не змінюється; наочно                                                                               | кожен споживач мусить пам'ятати; нове замикання на кожну підписку; для `removeEventListener` треба зберігати посилання |
| `ship.fire.bind(ship)` на місці виклику       | явно                                                                                                     | нова функція на кожен виклик `bind`; той самий ризик забути                                                            |
| Вільна функція `fire(ship)` без `this`        | `this` не потрібен взагалі                                                                               | втрачається ООП-інтерфейс і поліморфізм; логіка відривається від даних                                                 |

Обрано `bind` у конструкторі, бо у світі лише одне судно (копія на екземпляр коштує нічого), а
безпека не залежить від того, хто і як викличе метод: так вона працює і для таблиці прив'язок, і
для майбутнього DOM-обробника.

## Архітектурне обґрунтування: композиція замість глибокої ієрархії

Самонаведення має працювати і на кулі (ракета), і на астероїді («мисливець»), а підбір бонусу -
незалежно від того, що це за об'єкт. Тому ці механіки - **компоненти-дані** в `entity.components`
плюс **системи** в `behaviors.js` (`runBehaviors`, `applyPickup`):

```js
attachHoming(missile, { turnRate: 3.6, range: 560, targetKinds: ['asteroid'] });
attachHoming(asteroid, { turnRate: 0.55, range: 650, targetKinds: ['ship'] });
```

Один код самонаведення обслуговує обидва випадки: система повертає вектор швидкості до найближчої
цілі потрібного виду й не знає, чия це сутність. `pickup` - не клас, а `Entity` із компонентами
`pickup` (що робить) і `lifetime` (скільки лежить). Новий тип бонусу - це новий запис у таблиці
`EFFECT_HANDLERS`, а не новий клас.

**Як виглядало б «зламане» дерево успадкування:**

```
Entity
├─ Bullet
│  └─ HomingBullet          (копія коду самонаведення №1)
├─ Asteroid
│  └─ HomingAsteroid        (копія коду самонаведення №2)
└─ Pickup
   ├─ HealPickup
   └─ RapidPickup
```

- **Дублювання.** Самонаведення живе в двох гілках і розходиться: виправили в `HomingBullet` -
  забули в `HomingAsteroid`.
- **Комбінаторний вибух.** Із `N` незалежних поведінок потрібно до `2^N` підкласів. Захотіли
  «бонус, що тікає» або «ракету, що вмирає за таймером» - це ще класи.
- **Немає множинного успадкування.** У JavaScript у класу один батько, тож «мисливець, якого теж можна
  підібрати» не виразити без міксинів чи дубляжу.
- **Крихкий базовий клас.** Зміна в `Bullet` ламає `HomingBullet`, а `instanceof`-перевірки
  розповзаються по коду зіткнень.
- **Жорстка прив'язка до типу.** Клас об'єкта не змінити після створення, а компонент
  (`attachHoming`) можна приєднати до вже існуючої сутності навіть посеред гри.

Композиція це обходить: поведінки незалежні, комбінуються довільно, додаються в рантаймі й
перевіряються окремо. Ціна - рядкові ключі компонентів і потреба в дисципліні: систему треба
викликати з `World.step`. Для цього проєкту така ціна менша за ціну ієрархії.

## Prove It To Yourself — Результати експериментів

_Усі перевірки виконано в Node.js `v26.13.1` (`'use strict'`)._

### 1. Ланцюжок прототипів і власні властивості (`Object.getPrototypeOf` / `Object.hasOwn`)

Для екземпляра `s = new Ship(10, 100)` (`class Ship extends Entity`):

```text
Object.getPrototypeOf(s) === Ship.prototype                -> true
Object.getPrototypeOf(Ship.prototype) === Entity.prototype -> true
Object.hasOwn(s, 'x')                                      -> true
Object.hasOwn(s, 'hp')                                     -> true
Object.hasOwn(s, 'fire')                                   -> false
Object.hasOwn(Ship.prototype, 'fire')                      -> true
Object.hasOwn(Entity.prototype, 'move')                    -> true
```

**Висновок:** дані стану (`x`, `hp`) зберігаються як власні властивості на кожному екземплярі, тоді як методи (`fire`, `move`) існують в одному примірнику на прототипах класів і спільно використовуються всіма об'єктами.

### 2. Втрата контексту `this` без `.bind()` у strict-режимі

```text
const detached = s.fire;
detached();        // TypeError: Cannot read properties of undefined (reading 'hp')
s.fire.bind(s)();  // 100
```

**Висновок:** методи ES-класів завжди виконуються в strict-режимі; при передачі методу як колбеку без прив'язки `this` стає `undefined`, тому для обробників потрібні `.bind(this)` або стрілкова обгортка.

### 3. Імутабельність `Vector2`

```text
v1 = Vector2 { x: 3, y: 4 }
v2 = v1.add(new Vector2(1, 2)).scale(2) -> Vector2 { x: 8, y: 12 }
v1 === v2 -> false (v1 залишився { x: 3, y: 4 })
```

**Висновок:** операції `add`/`scale` повертають новий заморожений `Vector2`, не мутуючи вихідний вектор і виключаючи приховане спільне посилання між `pos`, `prevPos` та `vel`.
